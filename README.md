### Mercury

**C++20 Electronic Exchange Matching Engine**

[Repository](https://github.com/shashank-4bt/Mercury) · [Live](https://mercury-matching-engine.vercel.app)

## Skill Intelligence

The portfolio does not treat the skills section as a static list.

Skill-to-project relationships should be derived from actual GitHub codebase evidence wherever possible, including repository metadata, detected languages, README files, package manifests, dependency files, build configuration, source imports, and framework usage.

The goal is simple:

> **Where have I actually used this skill?**

The interface should show selected work for the currently selected or hovered skill.

Example:

```text
Kotlin

Selected work
├── Knowlyy
└── Android Development
```

The portfolio intentionally avoids skill ratings, stars, percentage bars, artificial proficiency scores, and unverified technology claims.

## Design Philosophy

The portfolio is designed as an **engineering interface rather than a conventional portfolio template**.

The visual language combines:

- Technical editorial layouts
- Asymmetric grids
- Hairline rules
- Coordinate systems
- Engineering diagrams
- Data-flow visualizations
- Mathematical notation
- Monospace technical metadata
- Large typographic hierarchy
- Restrained motion
- Dense information architecture

### Visual direction

```text
Near-black + Off-white + Neutral gray + One restrained accent
= Technical Editorial
```

The interface deliberately avoids:

- Purple / blue AI gradients
- Glassmorphism
- Giant glowing blobs
- Excessive rounded cards
- Generic SaaS layouts
- Stock imagery
- Fake testimonials
- Fake statistics
- Fake company logos
- Artificial project metrics
- Gratuitous 3D effects
- Generic AI-portfolio aesthetics

## Performance

The portfolio prioritizes a lightweight frontend:

- Minimal JavaScript
- Local font assets
- No unnecessary runtime APIs
- No runtime GitHub API dependency
- Efficient DOM manipulation
- CSS-first visual effects
- Static deployment compatibility

Skill intelligence should be generated during development/build time rather than requiring GitHub API requests for every visitor.
